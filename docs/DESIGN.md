# EchoSkillHub GitHub repository design

> Status: repository implementation complete; remote GitHub settings listed in
> `REPOSITORY_SETTINGS.md` still require maintainer configuration.

## Purpose and boundaries

EchoSkillHub is a static, GitHub-native Skill registry. It has no database or
long-running service:

```text
Pull request -> validation -> merged source -> immutable Release ZIP
                                              -> generated registry -> Pages
```

This repository defines contribution, validation, versioning, packaging,
publishing, indexing, deprecation, and revocation. It does not define a api,
installer, user interface, or Skill runtime.

## Sources of truth

| Information | Source |
| --- | --- |
| Name, description, and portable optional metadata | `SKILL.md` frontmatter |
| Skill content | `skills/<slug>/` reviewed in a pull request |
| Version increment | Exactly one `major`, `minor`, or `patch` PR label |
| Current published versions | GitHub Releases |
| Manifest | Generated by publishing and embedded in the ZIP |
| Release status overrides | Audited repository governance configuration |
| Public catalog | Registry rebuilt from release facts |

Contributors never submit `manifest.json` and never choose a numeric version.
For a new Skill, the selected increment is applied to `0.0.0`. When one pull
request changes multiple Skills, its single increment applies to all of them.

## Skill contract

A Skill lives at `skills/<slug>/` and contains exactly one root `SKILL.md`.
The directory slug and frontmatter `name` are equal. Frontmatter follows the
portable Agent Skills specification: `name` and `description` are required;
`license`, `compatibility`, `metadata`, and experimental `allowed-tools` are
optional. License files are included when the declaration or redistributed
content requires one.

Hub platform filtering is an optional extension stored inside the standard
`metadata` map as the string key `echoskillhub-platforms`. Its value is a
comma-separated unique subset of `windows`, `macos`, and `linux`. When absent,
the Manifest and Registry omit platforms rather than inferring support.

Validation rejects non-portable or escaping paths, links, case-insensitive path
collisions, generated manifests, secrets, prohibited executable content, and
content exceeding repository limits. Git cannot represent hard links as such;
local validation rejects linked filesystem inputs, while reviewed Git objects
remain ordinary files.

## Manifest and package

Publishing generates Manifest v1 from the six Agent Skills frontmatter fields,
the computed SemVer, and repository facts. The generated object is
schema-validated and added only to the ZIP. Hub-specific catalog fields are
derived only from namespaced string entries in the standard `metadata` map.

A release uses independent coordinates:

```text
tag:   <slug>-v<version>
asset: <slug>-<version>.zip
```

The ZIP root contains `SKILL.md`, generated `manifest.json`, and submitted
supporting files without an extra wrapping directory. Entries are sorted
and normalized with fixed timestamps, permissions, and compression parameters.
Repeated packaging of the same inputs is byte-identical.

A published `slug + version` is immutable. Before creating anything, publishing
checks the tag, target commit, release, asset name, size, and SHA-256. An exact
existing result is a recoverable success; any conflicting existing fact fails
closed. Fixes require a new version rather than replacing history.

## Registry v1

The complete registry is rebuilt from GitHub Releases rather than incrementally
editing old JSON. For every version, the builder verifies the canonical tag and
asset name, downloads the ZIP, recomputes size and SHA-256, reads and validates
the embedded Manifest, and checks the source commit and repository-owned URL.

The stable distribution address is:

```text
https://echoworker.github.io/EchoSkillHub/registry/v1/registry.json
```

The registry records schema version, generation time, repository, Skill
metadata, status, recommended version, and immutable version records. Version
records include publication time, source commit, download URL, size, SHA-256,
and status. Schema and cross-record invariants are checked before deployment.

`active`, `deprecated`, and `revoked` are maintained through reviewed
`governance/status.json` changes. Deprecated or revoked Skills require a concise
`statusReason`, which is copied into the Registry. Historical versions remain
represented. A revoked version cannot be recommended. A completely revoked Skill
has no installable recommendation; its history remains for audit. Registry
inclusion and digest verification do not certify that instructions or bundled
content are safe.

## Pull-request validation

`.github/workflows/validate.yml` runs in the `pull_request` context with only
`contents: read`. It checks out the pull-request merge, installs locked Node
dependencies, requires exactly one version label, runs tests and repository
checks, validates the changed Skills, and exercises deterministic packaging.
It has no release, Pages, environment, or secret permission.

Human review focuses on purpose, behavior, permission implications, external
services, credential requirements, provenance, redistribution rights, scripts,
network access, and whether the requested SemVer increment is appropriate.
CODEOWNERS identifies the required maintainers.

## Publishing and permissions

`.github/workflows/publish-skill.yml` runs for a closed
`pull_request_target` only when GitHub reports that the pull request was merged
into `main`. It checks out the trusted merge commit, revalidates the merged
change, determines changed Skill slugs, computes versions from the PR label, and
publishes each Skill independently.

The workflow separates trust and permissions:

- the release job alone has `contents: write`;
- registry construction has `contents: read`;
- the Pages deployment job alone has `pages: write` and `id-token: write`;
- all third-party actions are pinned to full commit SHAs;
- repository-level publishing concurrency uses `cancel-in-progress: false`.

Release assets are created before the registry can reference them. The Pages
artifact contains the complete site, so deployment replaces the registry as one
unit. If releases succeed but registry construction or Pages deployment fails,
the old public registry remains. Maintainers can use `workflow_dispatch` to
rebuild the registry from existing releases and redeploy it without republishing
or overwriting an asset.

## Failure and recovery model

| Failure | Result |
| --- | --- |
| PR validation fails | Merge is blocked; nothing is published |
| Existing tag targets another commit | Publish fails closed |
| Existing asset matches size and digest | Recovery continues idempotently |
| Existing asset conflicts | Publish fails; history is not overwritten |
| Release succeeds but registry fails | Public registry stays unchanged |
| Pages deployment fails | Previous complete artifact remains live |
| Concurrent publish starts | Runs serialize without cancellation |

Emergency deprecation or revocation is a minimal reviewed governance change,
followed by registry rebuilding and, when appropriate, a GitHub Security
Advisory. Deleting a Skill directory or silently deleting history is not the
withdrawal mechanism.

## Governance status

The repository now contains the workflows, CODEOWNERS, pull-request template,
contribution policy, security policy, schemas, scripts, tests, registry baseline,
and this implemented design. These committed controls are reviewable and
versioned.

GitHub-hosted controls cannot be enabled by repository files alone. Maintainers
must still create the exact version labels, configure the `main` ruleset and tag
protection, select GitHub Actions as the Pages source, configure the
`github-pages` environment, and verify organization Actions policy. The exact
manual checklist is in [Repository settings](REPOSITORY_SETTINGS.md). Until
those remote settings are applied, the corresponding protections must not be
described as active.
